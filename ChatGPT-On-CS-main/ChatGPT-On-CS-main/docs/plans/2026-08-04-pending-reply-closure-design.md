# 待回复闭环修复设计

## 目标

聚合接待定位失败时必须在数秒内恢复可操作状态；同一客户不得持续堆积重复待回复；客服已经在原平台人工发送消息后，对应记录应自动进入已回复。

## 方案

保留现有平台采集和定位方式，在统一状态层补闭环。定位请求使用短超时，失败只提示本条记录，不锁住整个列表。采集到稳定且完整的平台、店铺、账号、客户身份后，如果最新消息方向为客服发出，则把该精确会话下的 `pending/failed` 记录更新为 `sent`。当同一精确会话生成新建议时，旧的待回复记录更新为 `cancelled`，列表只留下最新问题。

历史记录继续在界面按四段精确身份折叠，不在每秒刷新接口里执行数据库维护，避免采集写入期间争抢数据库。新记录生成时才关闭同会话旧待回复，因此存量会随实际使用逐步收敛。

状态对账必须同时满足：会话稳定、置信度不低于 0.75、四段身份完整、消息历史不是复用缓存。千牛可额外使用采集脚本提供的 `latest_direction`；微信和企微使用结构化的最近消息方向。任何身份缺失或方向不明确的情况都不自动归档，避免串客户。

## 验证

单元测试覆盖稳定/低置信度/缓存历史/缺失身份、人工发送后的自动归档，以及同客户新问题对旧待回复的替换。回归测试覆盖定位错误后的快速恢复、列表一秒轮询刷新和新版桌面构建。
