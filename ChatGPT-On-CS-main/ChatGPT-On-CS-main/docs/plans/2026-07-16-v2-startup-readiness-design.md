# v2.0.0 启动就绪修复设计

## 问题

Electron 主进程会先加载渲染页面，再异步完成 Node 本地 API 服务初始化。当页面先挂载时，同步查询得到 `false`，随后依赖 `check-health` 事件切换主界面。Preload 已经移除了 Electron 原始事件参数，但主界面仍按 `(_event, health)` 接收，导致真正的健康值落在第一个参数、`health` 始终为 `undefined`，启动页永久停留。

同时，`/api/v1/base/health` 表示旧 Python 调度端是否通过 Socket.IO 在线，并不等同于 Node 本地 API 是否已经可以承载主界面。缺少可选旧后端时，该接口会返回 `false`；它不能作为整个 UI 是否允许进入的唯一条件。RAG、千牛、微信和企微采集器应继续通过各自健康接口展示独立状态。

## 方案选择

1. 仅延迟加载页面：能降低竞态概率，但不能消除竞态，不采用。
2. 让旧 Python 调度健康决定 UI：会让可选组件故障阻塞全部功能，不采用。
3. 推荐方案：以 Node Server `listen` 成功作为 UI 启动就绪；同步状态与异步事件共用同一严格布尔解析；旧调度端健康继续作为业务状态，不再控制启动页。

## 数据流

主进程注册 IPC → Node Server 开始初始化 → 渲染页同步读取 `get-health-status` → 若尚未就绪则订阅 `check-health` → Node Server 成功监听后保存状态并发送 `true` → 渲染页进入主界面并清理订阅。

## 可靠性与测试

- 抽取启动就绪订阅函数，覆盖“初始已就绪”“先未就绪、随后事件就绪”“false 不放行”“卸载时取消订阅”。
- 端到端冷启动验证必须在全新进程中完成，确认不按 `Ctrl+R` 也能进入主界面。
- 打包检查继续验证 Python、RapidOCR、RAG 完整依赖，并增加启动产物 smoke test。
- Release 替换时先上传并校验新附件，再删除错误附件，避免下载空窗。
